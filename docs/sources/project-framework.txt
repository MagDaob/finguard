明白。接下来按**完整系统的构建、调试和持续完善**来设计，重点是架构是否自洽、模块如何实现、故障如何定位，以及系统如何逐步获得更强的自主能力。

我建议把 FinGuard 的技术核心确定为：

> **能够动态规划任务、在明确授权内执行、通过业务证据验证结果，并从失败中改进规划策略的金融智能体系统。**

以下是调整后的工程设计。它属于拟议架构，具体可靠性需要通过实现和测试验证。

**一、先明确系统的五个核心对象**

原方案更多是在划分 Agent，但真正决定系统是否可靠的是：**任务、计划、授权、操作、证据之间的关系。**

| 核心对象 | 表示什么 | 关键约束 |
|---|---|---|
| Task：任务 | 用户希望达成的目标 | 保存原始需求、澄清结果与约束 |
| Plan：计划 | 如何达成目标 | 有版本、依赖关系和停止条件 |
| Approval：授权 | 用户允许执行什么 | 绑定具体操作或明确的授权范围 |
| Operation：操作 | 一次有业务含义的执行 | 具有稳定身份和独立状态 |
| Evidence：证据 | 如何确认执行结果 | 来自可追溯的业务记录 |

例如：

> “给小王转 300 元，转完至少保留 1000 元。”

它应被转换为：

- **任务**：向特定收款人付款，同时满足保留余额要求。
- **计划**：确认收款人 → 查询余额 → 预检 → 授权 → 提交 → 核实。
- **授权**：批准从指定账户向指定对象转出 300 元，并保留规定余额。
- **操作**：编号固定的一次转账。
- **证据**：交易状态、银行流水和余额变化。

**聊天记录不能替代这些业务对象。** 否则系统只能“记得自己做过什么”，却无法准确判断究竟发生了什么。

**二、总体架构：认知、控制、执行三个部分分别构建**

```mermaid
flowchart TD
    U["用户交互与授权"] --> C["认知系统：理解、规划、专业分析"]
    C --> P["计划控制：校验、调度、版本管理"]
    P --> G["执行控制：权限、风控、授权验证"]
    G --> E["业务执行：适配器、提交、结果核实"]
    E --> B["银行与外部服务"]
    B --> V["证据验证：业务结果与任务目标"]
    V --> P
    P --> U
    V --> L["离线评估与策略优化"]
    L --> C
```

其中，**安全控制是所有工具调用的必经边界**。读操作也要检查数据访问范围；写操作增加业务约束和授权验证。

三个部分分别承担不同职责：

| 部分 | 核心职责 | 输出 |
|---|---|---|
| 认知系统 | 理解需求、选择工具、提出方案 | 候选计划和业务解释 |
| 控制系统 | 判断计划合法性、决定执行条件、管理状态 | 可执行步骤或明确阻断原因 |
| 执行系统 | 调用业务接口、处理不确定结果、保存证据 | 经过核实的操作结果 |

数据库、任务队列、模型服务和日志系统是基础设施，不需要与业务职责混成一组“层级”。

**三、智能体结构：按推理职责分工，业务功能通过工具扩展**

建议采用**主规划器 + 专业分析智能体 + 计划审查器**，而不是为每个 API 都建立一个 Agent。

| 智能体 | 职责 | 权限边界 |
|---|---|---|
| 意图解析器 | 提取目标、对象、时间和约束 | 不执行业务操作 |
| 主规划器 | 分解任务、组织依赖、处理替代路径 | 提交候选计划 |
| 现金流分析智能体 | 消费分析、预算和资金需求解释 | 读取授权范围内的数据 |
| 产品分析智能体 | 产品信息对比、解释适用条件 | 不自行完成申赎 |
| 服务管理智能体 | 订阅、卡片和跨服务任务分析 | 提出待执行操作 |
| 计划审查器 | 检查遗漏、矛盾和可疑推断 | 提出修改建议或升级审查 |

这些是逻辑角色，可以共享模型，也可以使用不同模型。

**确定性程序已经能够准确完成的工作，应直接实现为工具。** 金额统计、余额校验、授权检查、交易状态查询，不需要经过额外一轮模型判断。

计划审查器也不能拥有最终放行权。两个模型可能共享同一种错误，模型之间达成一致不能证明操作合法。

**四、规划机制：支持动态规划，但必须经过“计划编译”**

完整系统应该能够处理新任务组合，固定模板可以作为可靠经验，但不应成为唯一能力来源。

推荐流程：

**需求解析 → 补全上下文 → 生成候选计划 → 静态校验 → 必要的模拟 → 执行 → 观察 → 局部重规划。**

这里的“计划编译”是将模型提出的方案转换成程序能够检查和运行的结构。

一个计划节点应包含：

```json
{
  "step_id": "transfer_01",
  "action": "transfer.create",
  "arguments": {
    "source_account_ref": "account_selected",
    "recipient_ref": "recipient_confirmed",
    "amount_minor": 30000,
    "currency": "CNY"
  },
  "depends_on": ["resolve_recipient", "check_funds"],
  "constraints": {
    "minimum_remaining_balance_minor": 100000
  },
  "success_condition": {
    "transaction_status": "SUCCEEDED"
  },
  "failure_policy": "STOP_DEPENDENTS"
}
```

工具注册表提供每个操作的：

- 参数与返回结构；
- 数据访问范围；
- 副作用类型；
- 授权要求；
- 幂等能力；
- 状态查询能力；
- 超时语义；
- 可撤销或补偿条件。

计划校验器依据这些定义检查计划，而不是依靠模型自己声称“安全”。

需要区分三类校验：

| 校验类型 | 检查内容 |
|---|---|
| 结构校验 | 工具是否存在、参数是否有效、依赖是否成环 |
| 语义校验 | 是否遗漏用户条件、是否把“查看”变成“修改” |
| 业务校验 | 账户是否可用、产品是否支持操作、资金是否满足约束 |

结构和明确业务规则由程序判断。语义校验可以结合模型审查，但对歧义仍需澄清，不能将模型置信度当成事实。

动态重规划还需要遵守两个规则：

1. **已完成操作成为既定事实，不能随意重新执行。**
2. **修改已批准操作的关键参数，必须重新获取适用授权。**

**五、执行机制：用持久化状态机处理现实中的不确定性**

任务编排与业务操作应使用不同的状态机。

任务可以处于：

`理解中、等待澄清、规划中、执行中、等待授权、部分完成、完成、终止。`

单个业务操作则可以处于：

`待准备、待授权、已授权、提交中、结果未知、成功、失败、提交前取消。`

这样才能表达：

> 账单分析已完成，订阅取消已成功，转账正在核实。

执行链路建议如下：

| 环节 | 主要动作 |
|---|---|
| Prepare | 解析资源标识、获取必要信息、形成操作草案 |
| Validate | 检查参数、业务约束、权限和前置条件 |
| Authorize | 获得绑定具体操作或明确范围的授权 |
| Commit | 提交前重新验证，执行业务请求 |
| Reconcile | 查询或接收业务结果，处理未知状态 |
| Verify | 判断结果是否满足任务目标 |
| Report | 根据证据生成用户可见结果 |

这里的 `Prepare` 只是应用层准备步骤。**除非业务接口明确支持，否则它不代表银行已冻结资金或提供了事务保证。**

三个细节必须在实现中落实：

- **稳定操作编号**：重试、恢复和重复点击不能产生新的同义操作。
- **未知状态核实**：超时后先确认原操作状态，不能直接重新付款。
- **检查点与业务状态分离**：工作流恢复不等于业务操作没有执行过。

LangGraph 的中断恢复可能重新运行节点，因此即使采用其持久化机制，带副作用的操作仍必须在业务层处理幂等。[docs.langchain.com](https://docs.langchain.com/oss/python/langgraph/interrupts?utm_source=chatgpt.com)

对于外部系统，不应笼统承诺“严格执行一次”。可实现的保证取决于下游是否提供幂等键、状态查询和稳定交易标识。

**六、授权机制：同时支持单次操作与受限委托**

如果每个步骤都要求用户点击，复杂任务体验会很差；如果批准一个模糊目标就允许所有操作，执行范围又会失控。

可以设计两类授权。

| 授权形式 | 适用情况 | 需要明确的内容 |
|---|---|---|
| 单次授权 | 转账、申赎、取消指定服务 | 对象、金额、账户、费用、有效期 |
| 受限委托 | 定期缴费、已知对象的重复任务 | 对象白名单、单笔上限、累计限额、频次、期限、撤销方式 |

受限委托只是系统设计能力，能否用于真实业务，还取决于银行支持的授权机制。

授权由服务端保存和验证，模型只能引用授权记录，不能自行创建或修改。执行组件需要校验授权主体、目标操作、有效期和使用状态；敏感参数改变后重新授权。这个原则也与 OWASP 的 Agent 安全建议一致。[cheatsheetseries.owasp.org](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html?utm_source=chatgpt.com)

还应提供统一的“停止任务”入口：

- 未提交操作立即停止；
- 已提交操作进入状态核实；
- 已完成操作按业务能力决定能否撤销；
- 持续委托可以被撤销，阻止未来执行。

**七、业务能力扩展：建立统一接口，保留各业务的真实语义**

可以完整支持转账、账单、理财、卡片、订阅和跨场景服务，但不能把所有操作都强行套成同一种事务。

| 业务 | 特别需要处理的语义 |
|---|---|
| 转账 | 收款人消歧、费用、到账状态、不可逆性 |
| 账单 | 统计口径、退款归属、币种、重复流水 |
| 理财 | 产品状态、风险匹配、交易窗口、申赎确认与到账区别 |
| 卡片 | 挂失与临时锁卡区别、设置生效范围 |
| 订阅 | 商户合同与代扣授权区别、生效时间、是否退款 |
| 跨场景服务 | 多服务部分成功、补偿条件、费用变化 |

跨场景任务应明确两类依赖：

- **数据依赖**：后一操作需要前一操作的结果。
- **业务条件依赖**：只有某个结果成立，才允许执行下一步。

例如“赎回到账后转账”，需要等待**资金实际可用**，不能只等待“赎回申请已受理”。

对于部分失败，可以采用补偿流程，但补偿本身也是业务操作，可能产生费用或需要新授权，不能被当作无成本回滚。

**八、调试体系：让错误可以定位、复现和比较**

调试需要同时覆盖模型行为和业务状态。建议建立三套工具。

**1. 任务轨迹查看器**

每个任务展示：

- 用户需求与澄清记录；
- 提取的约束；
- 每一版计划及修改差异；
- 工具输入、输出与耗时；
- 策略判定与授权记录；
- 状态迁移；
- 最终证据。

记录结构化决策摘要即可，不需要依赖模型隐藏推理过程。敏感账户信息、令牌和个人数据应脱敏，访问日志也需要权限控制。

**2. 场景回放器**

保存可复现的测试包：

```text
初始业务状态
用户输入与确认事件
工具返回或故障脚本
模型与提示词版本
工具和规则版本
预期最终状态
```

分成两种回放：

- **固定模型输出回放**：检查控制和执行代码是否稳定。
- **重新调用模型回放**：检查模型、提示词或规划策略变化的影响。

这能避免把模型随机变化误判为后端故障。

**3. 故障注入器**

主动模拟：

- 请求发送前断网；
- 操作已生效但响应丢失；
- 同一请求重复到达；
- 回调重复或乱序；
- 用户确认后余额变化；
- 两个任务同时支出；
- 服务重启；
- 下游接口结构变化；
- 工具返回中夹带恶意指令。

关键不是让界面显示一条报错，而是检查**最终账本、授权和操作状态是否仍然正确**。

**九、测试体系：先定义不可破坏的性质，再测试功能**

建议把以下条件作为系统不变量：

1. 没有有效授权，写操作不得生效。
2. 执行参数必须处于授权范围内。
3. 同一业务操作不得因重试重复记账。
4. 不得通过并发操作突破余额或授权限额。
5. 不得访问其他用户的数据。
6. 没有业务证据，不得报告成功。
7. 外部文本不得改变工具权限或授权状态。
8. 系统恢复后，已完成操作不得被当作未执行操作重放。

测试由内向外推进：

| 测试层 | 主要验证内容 |
|---|---|
| 单元测试 | 金额计算、约束判断、状态迁移 |
| 契约测试 | 工具与适配器输入输出及异常语义 |
| 属性测试 | 大量随机操作序列下，不变量是否成立 |
| 并发测试 | 重复提交、竞争扣款、授权重复消费 |
| 故障恢复测试 | 超时、重启、回调丢失后的最终状态 |
| 智能体评估 | 意图理解、规划正确性、澄清质量 |
| 端到端测试 | 用户目标是否完成，是否产生额外副作用 |

评估成功率时，应把两件事分开：

- **业务完成率**：合法且信息充分的任务是否完成。
- **正确处置率**：信息不足、权限不足或无法执行时，是否采取正确措施。

安全拒绝不能简单算成业务成功，业务完成也不能掩盖越权行为。

**十、持续完善：建立“失败分类—局部修复—回归验证”的闭环**

系统改进不能一律靠修改提示词。建议按失败所在层分类：

| 失败类型 | 优先修复位置 |
|---|---|
| 未理解“至少保留 1000 元” | 意图提取与约束表示 |
| 计划遗漏授权步骤 | 计划编译与校验 |
| 模糊对象被错误匹配 | 实体解析与澄清策略 |
| 超时后重复扣款 | 执行器、幂等与适配器 |
| 工具成功但任务仍未完成 | 成功条件与结果验证 |
| 不必要的多轮询问 | 对话策略与上下文管理 |
| 模型调用成本过高 | 任务路由、缓存、模块划分 |
| 恶意数据影响操作 | 信任边界与工具权限 |

“自演进”可以构建为一条独立流水线：

**收集失败 → 归因 → 生成改进候选 → 隔离评估 → 回归测试 → 审核发布 → 监测与回退。**

允许优化的对象包括：

- 提示词；
- 规划模板；
- 工具选择策略；
- 澄清方式；
- 专业模块路由；
- 非敏感偏好记忆。

权限规则、授权验证和账本逻辑不由智能体在线自行改写。它们的更新进入正常的软件变更与测试流程。

工程构建可以沿依赖关系依次推进：**业务状态与工具契约 → 可靠执行内核 → 授权与策略控制 → 任务编排 → 动态规划与专业智能体 → 回放评估 → 离线优化。** 每增加一层，都需要证明它在既有不变量成立的前提下，确实提高了任务完成能力。
