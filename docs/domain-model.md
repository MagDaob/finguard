# 领域模型

本文定义首轮实现的建模要求，来源为[原始框架](sources/project-framework.txt)。字段为设计草案，正式类型和存储结构尚未实现。

## 核心对象

| 对象 | 含义 | 建议保留的信息 |
|---|---|---|
| Task（任务） | 用户目标及约束 | 稳定编号、主体、原始需求、澄清、约束、状态、成功条件 |
| Plan（计划） | 达成目标的可版本化方案 | 任务编号、版本、节点、依赖、停止条件、审查结果 |
| Approval（授权） | 用户允许执行的操作或范围 | 主体、目标、参数或范围、期限、限额、使用与撤销记录 |
| Operation（操作） | 一次具有稳定身份的业务执行 | 编号、任务关联、计划引用、参数、状态、授权引用、下游标识 |
| Evidence（证据） | 可追溯的业务结果记录 | 操作编号、来源、业务记录标识、采集时间、结果及验证状态 |

一个任务可以有多个计划版本。计划节点引用业务操作；重规划沿用已执行操作身份。一个操作可以关联多条证据。

授权匹配操作内容，不能仅依赖任务编号或计划节点编号。相同操作编号发生关键参数冲突时，应阻断执行。

工具注册表、状态迁移记录和版本信息是支撑结构，不替代上述业务对象。

## 状态分离

以下为状态集合草案。合法迁移、触发事件及持久化协议在领域模型阶段定义。

| 对象 | 状态 |
|---|---|
| 任务 | 理解中、等待澄清、规划中、执行中、等待授权、部分完成、完成、终止 |
| 操作 | 待准备、待授权、已授权、提交中、结果未知、成功、失败、提交前取消 |

授权的有效、过期、撤销和消费语义需单独建模。操作“已授权”不代表提交时授权仍然有效，提交前必须复检。

任务可部分完成，同时包含成功和结果未知的操作。成功操作不会因工作流恢复被当作未执行操作。

## 数据表达

- 金额使用最小货币单位的整数，并带显式币种。人民币示例以分为单位。
- 费用、支出金额和最低保留余额分别表达，避免混淆校验口径。
- 主体和资源归属作为访问校验输入，引用标识本身不代表访问权限。
- 时间、版本和参数规范化规则在实现中统一定义，支持授权匹配和审计。
- 任务约束、操作成功条件和最终任务成功条件分别保存。
- 工具输出及外部文本作为数据处理，不能修改系统权限或生成授权。

## 首个场景

[转账场景](../tests/scenarios/transfer-basic.json)使用虚构主体和账户。初始余额为 1,500 元，转账 300 元，费用为 0 元，最低保留余额为 1,000 元。

预期转账后余额为 1,200 元。成功还需满足有效授权、单次记账、业务证据完整，以及任务目标验证通过。

该文件是测试输入草案，不是运行配置、正式接口或有效授权。场景加载器尚未实现。
