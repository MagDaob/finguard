# 领域模型

本文说明领域对象与后端持久化，来源为[原始框架](sources/project-framework.txt)。数据类型位于 [models.py](../src/finguard/domain/models.py)，数据库结构位于 [初始迁移](../src/finguard/backend/migrations/001-initial.sql)。

## 核心对象

| 对象 | 含义 | 建议保留的信息 |
|---|---|---|
| Task（任务） | 用户目标及约束 | 稳定编号、主体、原始需求、澄清、约束、状态、成功条件 |
| Plan（计划） | 达成目标的可版本化方案 | 任务编号、版本、节点、依赖、停止条件、审查结果 |
| Approval（授权） | 用户允许执行的操作或范围 | 主体、目标、参数或范围、期限、限额、使用与撤销记录 |
| Operation（操作） | 一次具有稳定身份的业务执行 | 编号、任务关联、计划引用、参数、状态、授权引用、下游标识 |
| Evidence（证据） | 可追溯的业务结果记录 | 操作编号、来源、业务记录标识、采集时间、结果及验证状态 |

一个任务可以有多个计划版本。计划节点引用业务操作；重规划沿用已执行操作身份。一个操作可以关联多条证据。

授权匹配操作内容，不能仅依赖任务编号或计划节点编号。相同操作编号发生关键参数冲突时，应阻断执行。

工具注册表、状态迁移记录和版本信息是支撑结构，不替代上述业务对象。

## 状态分离

状态集合与合法迁移已在 [states.py](../src/finguard/domain/states.py)定义。后端使用迁移守卫，并在同一事务内保存状态修改与事件。读操作在权限检查后可由准备进入提交，不需要虚构写授权。

| 对象 | 状态 |
|---|---|
| 任务 | 理解中、等待澄清、规划中、执行中、等待授权、部分完成、完成、终止 |
| 操作 | 待准备、待授权、已授权、提交中、结果未知、成功、失败、提交前取消 |

单次授权以 ACTIVE、REVOKED 和 CONSUMED 保存；过期按可信时间计算。操作“已授权”不代表提交时授权仍然有效，提交前必须复检。

任务可部分完成，同时包含成功和结果未知的操作。成功操作不会因工作流恢复被当作未执行操作。

操作终态不能迁移回提交状态。结果未知仅允许核实为成功或失败；提交中和结果未知的操作均不能标记为提交前取消。缺少授权的状态不能直接迁移到提交中。

状态类型和历史是否合法是两个问题。反序列化出的状态值不证明曾经经过合法迁移；执行服务检查可信状态并保存迁移记录。

## 数据表达

- 金额使用最小货币单位的整数，并带显式币种。人民币示例以分为单位。
- 费用、支出金额和最低保留余额分别表达，避免混淆校验口径。
- 主体和资源归属作为访问校验输入，引用标识本身不代表访问权限。
- 时间、版本和参数规范化规则在实现中统一定义，支持授权匹配和审计。
- 任务约束、操作成功条件和最终任务成功条件分别保存。
- 工具输出及外部文本作为数据处理，不能修改系统权限或生成授权。

当前模型仅支持 `CNY`，整数分范围为 0 至 `2**63 - 1`。转账金额必须大于 0。金额字段拒绝字符串、布尔值和浮点数。费用和最低保留余额必须显式给出。

模型使用严格校验，拒绝多余字段；容器使用元组。计划结构检查覆盖重复节点、缺失依赖和依赖成环。首个任务的绑定检查限定为一个转账操作，并核对主体、任务、操作编号及完整参数。

`Approval` 目前记录单次授权的结构、时区时间和状态。构建该模型不代表获得有效授权。可信签发、匹配、撤销和消费由后端授权服务处理。

`Evidence` 记录来源、业务记录编号和采集时间，并区分交易状态、流水和余额。后端通过模拟银行权威记录及流水验证结果；真实下游证据适配另行实现。

转账查询契约区分 `FOUND`、`NOT_FOUND` 和 `UNKNOWN`。查询未找到记录仅表示该次观察没有结果，不能据此证明原操作从未生效。找到交易时须提供业务编号和状态；其余观察不能附带已确认交易结果。

## 首个场景

[转账场景](../tests/scenarios/transfer-basic.json)使用虚构主体和账户。初始余额为 1,500 元，转账 300 元，费用为 0 元，最低保留余额为 1,000 元。

预期转账后余额为 1,200 元。成功还需满足有效授权、单次记账、业务证据完整，以及任务目标验证通过。

该文件已可通过 `finguard validate-scenario` 加载，格式版本为 `0.1`。加载器检查初始资源、金额计算、事件引用和成功条件的一致性，并生成确定编号的任务、计划及操作草案。

模拟确认事件不会转换为有效授权，模拟业务结果不会转换为实际成功。场景命令仅报告校验结果和预期余额，操作保持 `PREPARING` 状态。

## 后端记录关联

`domain/models.py` 保留首个单转账领域切片的绑定模型；多业务 HTTP 请求和计划由 `backend/catalog.py` 定义。两者复用整数金额、资源引用和状态规则，首个切片模型不承担多业务运行存储。

| 存储 | 关联与约束 |
|---|---|
| `tasks` | 主体与客户端请求编号唯一，保存目标、约束及推进请求 |
| `plans` | 任务与版本唯一，节点引用稳定操作编号 |
| `operations` | 关联主体、任务、节点、动作和完整参数摘要 |
| `approvals` | 绑定主体、操作、摘要、有效期与消费状态 |
| `delegations`、`authorization_uses` | 白名单、单笔与累计限额、频次及一次性消费记录 |
| `evidence` | 关联操作、主体、类型和权威业务记录 |
| `bank_commands`、`bank_ledger` | 独立业务结果、稳定幂等编号和唯一入账流水 |
| `task_events`、`callback_events` | 状态轨迹、回调去重与内容摘要 |

参数摘要包括主体、动作和规范化 JSON 参数。计划修改关键参数后产生新操作，旧单次授权失效；已完成及待核实操作作为事实保留。已失败或提交前取消的节点不重新激活。

委托预算消费与提交意图原子保存。未知结果占用预算；明确失败仅释放预算，保留尝试频次。运行数据库和回放数据库使用不同命名空间，离线评估不能改写运行中的业务状态。
