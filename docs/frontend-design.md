# 前端工作台设计方案

2026 年 10 月 29 日，用户要求重做前端结构与风格。后续视觉与交互提案改为[对话式任务与成果面板](frontend-redesign.md)。本文保留首版设计和业务约束，供已实现版本追溯；新版目前仅完成设计。

设计日期：2026 年 10 月 27 日。依据：0.3.0 模拟业务后端，设计时的代码基线为 `304f9be`。本文保留设计与验收要求；现已实现 F1 至 F3 的现有接口范围，实际选型、联调结果和限制见[前端验收记录](frontend-validation.md)。F4 仍待后续实现。

## 产品定位与设计取舍

建议把 FinGuard 设计成“可确认、可追踪、可核实的金融任务工作台”。用户用自然语言表达目标，通过结构化卡片确认参数，并随时查看执行进度与结果凭证。

首版面向使用模拟账户的个人用户和项目验收人员，以桌面浏览器为主。日常业务与开发调试使用独立导航。界面持续显示“模拟环境”，金额、产品和业务结果均属于虚构数据。

用户应在每个任务中看清四件事：系统准备做什么、哪些操作需要确认、当前实际发生了什么、结果有什么依据。默认突出任务和下一步行动，技术编号与原始事件按需展开。

| 取舍 | 推荐 | 原因 |
|---|---|---|
| 产品入口 | 自然语言输入与常用任务入口并存 | 既保留智能体体验，也为有限语法提供明确表单 |
| 主体布局 | 任务导航、任务详情、上下文检查区 | 同屏关联目标、计划、授权和证据 |
| 计划展示 | 纵向步骤为默认，依赖图留给复杂任务 | 普通用户先理解先后条件，无须学习节点编辑器 |
| 结果表达 | 独立结果卡与凭证 | 对话文本不能替代业务状态 |
| 首页内容 | 待处理任务、当前任务与新建入口 | 当前重点是可靠执行；收益预测和投资推荐不在首版范围 |
| 发布方式 | 后续采用独立前端构建，同源访问现有后端 | 复用 FastAPI 控制边界，保持银行服务与浏览器隔离 |

## 页面与导航

以下路径均为拟议前端路由，尚未创建。

| 页面 | 路由 | 主要内容 | 优先级 |
|---|---|---|---|
| 任务工作台 | `/tasks`、`/tasks/:taskRef` | 新建任务、任务列表、计划、待确认操作、结果与凭证 | 首版 |
| 账户与账单 | `/accounts`、`/accounts/:accountRef` | 账户余额、分页流水、账单查询入口与报告 | 首版 |
| 授权管理 | `/authorizations` | 委托列表、范围、剩余预算和撤销；单次授权先从任务进入 | 第二阶段 |
| 产品与持仓 | `/products` | 模拟产品、风险匹配、交易窗口、申购和赎回任务入口 | 第二阶段 |
| 卡片与订阅 | `/services` | 临时锁卡、恢复、订阅合同取消 | 第二阶段 |
| 调试与评估 | `/lab`、`/lab/tasks/:taskRef` | 轨迹、计划版本、回放、候选对照、审核发布 | 第三阶段 |
| 连接与设置 | `/settings`、`/settings/integrations` | 当前主体、会话、提供方目录和配置格式校验 | 分阶段 |

首版只显示已交付页面。后续导航不作为可点击的空壳入口。工作台中的“查看诊断”仅在具备权限时出现；业务权限与评估权限由 `/v1/me` 返回，服务端负责最终检查。

任务列表首版采用“加载更多”。现有接口按引用编号分页，并非按业务时间排序；可显示创建时间，但不能把第一页标为完整的“最近任务”。列表内筛选仅作用于已加载记录，界面注明范围。全局检索、按日期排序和跨任务待确认队列需要新增接口。

## 工作台布局

### 桌面与窄屏

建议桌面设计基准为 1440 × 900。左侧导航约 208 px，中央任务区自适应，右侧检查区约 344 px。主内容间距为 24 px，页面留白为 24～32 px。

```text
┌──────────────────────────────────────────────────────────────┐
│ FinGuard        模拟环境                    当前主体 / 设置   │
├──────────────┬─────────────────────────┬─────────────────────┤
│ 新建任务     │ 给小王转 300 元          │ 待确认操作           │
│              │ 待你确认 · 计划版本 1    │ 收款人 / 付款账户    │
│ 任务工作台   │                         │ 金额 / 费用 / 约束   │
│ 账户与账单   │ 原始目标                 │                     │
│              │ 计划步骤与依赖           │ 确认本次操作         │
│ 已加载任务   │ 已完成事实 / 当前进展    │                     │
│ · 任务 A     │                         │ 授权范围 / 结果凭证  │
│ · 任务 B     │ 补充信息或明确发起关联查询│ 按当前状态切换       │
└──────────────┴─────────────────────────┴─────────────────────┘
```

这是空间结构示意，右侧内容取决于所选操作。任务只包含一个转账操作时，不把内部的余额检查、提交和核实伪装成额外计划节点；这些过程展示在该操作的进度中。

- 宽度不小于 1280 px：显示三栏，确认参数与任务目标同时可见。
- 768～1279 px：收起全局导航；操作详情进入侧栏或详情页，保持完整确认内容。
- 小于 768 px：单栏任务详情，按“目标、计划、当前行动、凭证”排序。确认使用完整页面，金额与收款人同时可见。
- 320 px：表单、提示和按钮换行；金额与币种不被截断。复杂轨迹表格可局部横向滚动。

### 新建与澄清

空状态标题为“今天想完成什么？”。提供余额、转账、账单三个首版入口。示例为“给小王转 300 元，至少保留 1,000 元”和“看看上个月的餐饮支出”。选择示例只填入输入框，由用户提交。

提交按钮为“生成任务计划”。只读任务在明确提交后可以调用 `run`；含写操作的任务进入预览与确认。界面显示“正在生成计划”，不模拟逐字推理或虚构已完成步骤。

发生 `WAITING_CLARIFICATION` 时，显示服务端 `questions`。当前没有自然语言澄清续写接口；首版通过已支持业务的结构化表单补全目标，再提交 `plans` 与 `expected_version`。多目标请求须逐项列出，不能只补全其中一项。无法完整表达时保留任务待澄清，不把自由输入自动当作有效计划。

“还剩多少”可显式关联前一任务，界面展示“关联任务：给小王转 300 元”。它创建新的余额查询任务，并重新查询余额。收款人、金额与授权不从上下文自动继承。其他付款指代要求用户补全。

### 转账确认

确认面板由 `preview` 的真实字段驱动。收款人使用已确认资源的显示名，付款账户使用资源名称或明确的账户引用。后端未返回银行卡尾号时，界面不编造尾号。

| 内容 | 示例 | 数据来源 |
|---|---|---|
| 收款人 | 小王 | `preview.recipient_name` |
| 付款账户 | 当前模拟账户及引用 | 操作参数与账户目录 |
| 转账金额 | ¥300.00 CNY | `amount_minor: 30000` |
| 手续费 | ¥0.00 CNY | `fee_minor: 0` |
| 当前可用余额 | ¥1,500.00 CNY | `preview.available_balance_minor` |
| 预计转账后余额 | ¥1,200.00 CNY | 当前余额减金额及费用，明确为预估 |
| 最低保留余额 | ¥1,000.00 CNY | `minimum_remaining_balance_minor` |
| 确认范围 | 本操作、当前参数、默认 5 分钟 | 操作编号、摘要与申请期限 |

主按钮使用“确认转账 ¥300.00”，次按钮为“修改未提交步骤”。提示“确认后将请求执行；实际余额以提交时复检及结果凭证为准”。确认期间停用重复点击，不先行显示扣款或成功。

确认顺序：重新取得任务及预览，展示完整参数，提交 `expected_digest`，确认服务端授权结果，再请求 `run`。若任务已请求运行，后台可能在授权后立即推进；界面不得提供“授权成功后再决定是否执行”的承诺。

确认时发生版本冲突或参数变化，展示旧值与新值，重新要求用户确认。前端不能自行把旧摘要替换成新摘要再发送。网络中断时，先读取该操作的授权记录和任务状态，不盲目再签发授权。

`authentication_policy.step_up_required` 为真且服务不可用时，面板显示“此操作需要额外验证，当前验证服务尚未接入”。停用确认按钮，允许查看详情或修改未提交步骤。门槛来自服务端策略，前端不硬编码 1,000 元，不制作会显示验证成功的模拟短信输入框。

## 状态与异常交互

任务与操作分别展示状态。任务状态是整体进展，操作状态描述一次具体业务。所有派生提示均需有服务端字段或事件支撑。

| 服务端状态或条件 | 界面文案 | 允许的主要行动 |
|---|---|---|
| `UNDERSTANDING` / `PLANNING` | 正在理解需求 / 正在生成计划 | 查看原始目标，等待结果 |
| `WAITING_CLARIFICATION` | 需要补充信息 | 补全目标，查看未理解内容 |
| `WAITING_APPROVAL` | 等待你的确认 | 查看预览并逐项确认；额外验证不可用时阻断 |
| 操作 `AUTHORIZED` | 已确认，等待执行 | 查询当前状态；尚未消费时可撤销授权 |
| `EXECUTING` / 操作 `SUBMITTING` | 正在执行 / 正在提交 | 查看进展；请求停止后续步骤 |
| 操作 `UNKNOWN` | 结果待核实 | 刷新原操作；不出现“重新转账” |
| 赎回已受理且尚无到账证据 | 已受理，等待到账 | 查看结算进展；依赖付款继续等待 |
| `PARTIALLY_COMPLETED` | 部分完成 | 列出已完成、待核实和未完成步骤 |
| `COMPLETED` 且 `verified_success: true` | 已完成并核实 | 查看凭证与执行时余额 |
| `COMPLETED` 但证据校验未通过 | 完成状态待核验 | 刷新详情与诊断，不展示成功凭证 |
| `TERMINATED` | 任务已终止 | 查看各操作最终结果，不暗示全部撤销 |
| 操作 `FAILED` | 此步骤失败 | 解释原因；符合条件时创建新的尝试并重新确认 |
| 操作 `CANCELLED_PRE_SUBMIT` | 提交前已取消 | 查看记录，不恢复该节点 |

“等待到账”不是新的任务枚举，也不能由等待时长推断。没有明确受理或结算信息时，仅显示“结果待核实”。任务列表本身没有 `verified_success`，须取得详情后才显示“已完成并核实”。

停止按钮使用“停止后续步骤”。确认说明为“未提交步骤将取消；已提交操作继续核实，已完成结果保留”。收到停止响应后展示 `stop_requested` 和各操作现状，不能用一个成功提示替代后续核实。

部分完成示例：赎回已经到账，后续转账因余额约束失败。界面保留赎回事实与凭证，显示转账失败原因。新计划只修改允许变更的步骤，保留已完成和待核实操作的身份及参数。

| 异常 | 界面处理 |
|---|---|
| 创建任务响应丢失 | 当前会话保留同一请求编号与完整请求，按原请求查询式重试；不自动创建新编号 |
| 页面刷新后无法恢复原请求 | 提示先核对已有任务；当前缺少按请求编号检索接口，不能保证自动定位 |
| 401 | 显示会话失效，清除敏感缓存，要求重新建立访问会话 |
| 403 / 404 | 显示无权执行或资源不可访问，不泄露其他主体信息 |
| 409 | 按稳定错误码展示版本冲突、业务条件变化或执行占用；读取最新状态 |
| 422 | 将错误定位到字段，不清空其他合法输入 |
| 503 / 断网 | 保留最近一次状态并显示“更新中断”和最后读取时间；已有操作结果仍需核实 |
| 未识别状态或字段 | 保守显示“暂无法识别”，提供诊断信息，禁止默认映射为成功 |

## 结果、业务页面与授权

结果卡按任务目标组织，并保留任务、计划版本、操作和证据之间的可追溯关系。普通视图显示结果、金额、收款人、核实时间和凭证入口；展开后显示操作编号、业务记录引用与证据来源。

余额标明“执行时余额”或“当前查询余额”，并带时间。其他任务可能已改变账户，不能把旧转账凭证中的余额当作实时余额。凭证默认展示面向用户的摘要，原始 JSON 留在诊断区。

| 业务 | 主要展示 | 必须保留的语义 |
|---|---|---|
| 账单 | 支出、退款、净支出、分类条形图与流水 | 已入账现金流；排除内部转账和理财流动；无匹配记录显示零 |
| 日期区间 | 自然月或明确起止日期 | 展示时可用包含式日期；请求结束日期不包含，时区为 `Asia/Shanghai` |
| 产品 | 模拟固定价值、风险匹配、交易窗口和持仓 | 不虚构收益率、行情曲线或预测收益 |
| 赎回 | 受理、结算、到账证据 | 受理不等于到账；实际到账后再解锁后续付款 |
| 卡片 | 临时锁定状态与恢复入口 | 不称作永久挂失或销卡；恢复创建新任务并重新确认 |
| 订阅 | 合同状态及取消结果 | 退款为零，代扣授权未变更；不称作关闭全部扣款 |
| 委托 | 收款人白名单、单笔及累计限额、频次周期、期限、剩余预算 | 多项限制同时生效；未知操作占用预算；明确失败释放预算但保留尝试次数 |

首版单次授权记录放在对应任务中。委托管理使用现有分页接口，列表数量只反映已加载范围。全局单次授权搜索、完整待确认中心、跨任务时间筛选列入后端补充项。

导出按钮使用“导出任务记录”，说明已应用有限脱敏规则，并建议用户检查内容。导出只含首批最多 1000 条轨迹；若提供“完整轨迹”，必须使用 `after` 分页补齐并验证顺序和去重。不能把 `contains_credentials: null` 显示成“无敏感信息”。

## 调试、评估与扩展设置

调试区展示结构化事件时间线、计划版本差异、操作状态、授权关联和证据。模型规划只显示轮次、耗时、用量及工具状态；未知用量显示“未提供”，不伪装为零，也不展示隐藏推理过程。

评估区需要 `evaluation.manage`，并以服务端启用状态为准。按“套件、运行结果、候选对照、人工审核、发布记录”组织。当前只有候选按编号读取接口；跨会话候选列表与完整发布历史需补接口。首期可从本次创建结果进入详情，不能展示虚构的全量历史。

发布确认展示评估摘要和基线，发送当前 `expected_evaluation_digest` 与明确审核结果。评估通过不自动触发发布。回退入口单独确认，业务操作和授权不随策略回退。

连接设置展示提供方、协议支持与格式校验结果。按钮命名为“校验配置格式”，不叫“连接成功”或“启用插件”。密钥只使用引用字段；不在前端采集、展示或保存银行与模型的真实密钥。真实连接持久化、密钥管理及插件执行属于后续建设。

## 视觉与组件规范

建议采用浅色金融工具风格：雾灰背景、白色内容面板、深色文字、低饱和青绿色主操作。用留白和细分隔线划分区域，避免大面积渐变、发光和持续动画。暗色主题遵循同样的层级，作为后续可验收能力。

| 设计项 | 建议值或规则 |
|---|---|
| 浅色基础色 | 背景 `#F5F7F8`；内容面板 `#FFFFFF`；正文 `#18232A`；次级文字 `#53636B` |
| 主操作 | `#126B5B`，配白色文字；同一行动区只保留一个主要按钮 |
| 状态 | 待确认用琥珀色，核实中用蓝色，已核实用绿色，失败用红色；始终附文字和图标 |
| 字体 | 系统中文无衬线字体；正文 14～16 px，辅助信息不小于 12 px，页面标题 24～28 px |
| 金额 | 24～32 px，使用等宽数字；始终保留币种，零费用与未知费用分别展示 |
| 间距 | 4、8、12、16、24、32 px；内容面板圆角 12 px，按钮圆角 8 px |
| 数据密度 | 普通用户保留关键摘要；原始参数、编号和轨迹可展开 |
| 动效 | 仅用于真实状态变化和面板切换；尊重减少动态效果设置 |

建议抽取 `TaskComposer`、`TaskList`、`TaskHeader`、`PlanSteps`、`OperationPreview`、`ApprovalPanel`、`StatusNotice`、`EvidencePanel`、`MoneyText`、`TraceTimeline` 和 `ConflictDiff`。组件名属于方案，尚未生成源码。

可访问性目标参考 [WCAG 2.2](https://www.w3.org/WAI/WCAG22/quickref/)：常规文字对比度至少 4.5:1；关键控件有键盘焦点；触屏操作区建议不小于 44 × 44 px。确认页按“收款人、金额、约束、行动”组织阅读顺序。状态更新通过适度的屏幕阅读器通知呈现，不每次轮询都播报。

## 前端技术方案

以下均为候选选型。本次不安装依赖、不创建前端工程、不修改后端接口，也不将这些工具写入“已采用”清单。

| 层次 | 建议 | 取舍 |
|---|---|---|
| 应用 | React、TypeScript、Vite | 适合已有 API 的交互工作台；需自行组织路由与数据层，无首版服务端渲染需求 |
| 路由 | React Router | 任务与凭证可通过稳定地址打开，并恢复当前选择 |
| 服务端数据 | TanStack Query | 集中处理缓存、轮询和失效；授权及资金状态仍以服务端为准 |
| 组件基础 | Radix Primitives 加项目设计样式 | 复用焦点和键盘交互基础，业务卡片由项目定制；原生控件足够时优先原生 |
| 样式 | CSS 自定义属性与 CSS Modules | 先固定颜色、间距和状态语义，避免首版同时维护多套组件体系 |
| 接口类型 | 从 FastAPI OpenAPI 生成基础类型，加运行时边界检查 | 当前部分动态响应未完整声明类型，须补响应模式或维护经核对的适配层 |
| 本地状态 | 组件状态及必要的上下文 | 只存输入草稿、选中项与展开状态，避免复制一套业务状态机 |
| 验证 | 组件交互检查与浏览器端到端检查 | 优先覆盖重复点击、冲突、未知结果、恢复和凭证，不以截图替代业务验证 |

React 官方列出 [Vite 的 React + TypeScript 入口](https://react.dev/learn/build-a-react-app-from-scratch)，同时说明自建路由与数据层的维护代价。缓存方案依据 [TanStack Query 文档](https://tanstack.com/query/latest/docs/framework/react/overview)，交互基础依据 [Radix 可访问性说明](https://www.radix-ui.com/primitives/docs/overview/accessibility)。具体版本与包管理器在进入实现阶段时锁定，本次不冻结版本。

业务数据按主体和资源编号建立缓存键。切换身份、退出或令牌失效时清空任务、账户、预览和授权缓存。前端只访问 FinGuard API，银行、模型和数据库凭据均留在服务端。

开发验收可使用会话内的 Bearer 令牌输入，令牌仅保存在内存，不进入地址栏、浏览器长期存储或日志。刷新后重新建立会话，并通过任务编号恢复查看。普通退出仅清除本机会话；“撤销当前令牌”是明确的服务端操作。正式登录、会话续期、HttpOnly Cookie 及相应的跨站请求防护需作为独立后端阶段设计。

金额输入保留十进制字符串，按整数算法转换为分，拒绝负数、超出小数位和非法格式。当前 JSON 使用数字整数，必须明确 JavaScript 安全整数边界；大整数响应须在解析阶段无损处理或由服务端限定范围，不能先按浮点数解析再补救。前端不得擅自将接口金额改成字符串。展示计算仅用于说明，业务约束仍由服务端复检。

## 接口衔接与缺口

| 交互 | 当前可用接口 | 限制或后续工作 |
|---|---|---|
| 主体与权限 | `GET /v1/me` | 无完整登录、续期和用户资料系统 |
| 任务列表与详情 | `GET /v1/tasks`、`GET /v1/tasks/{id}` | 无全局搜索、状态过滤和业务时间排序 |
| 生成任务 | `POST /v1/tasks` | 同请求编号与完整内容支持幂等；无按请求编号单独检索 |
| 补全与重规划 | `POST /v1/tasks/{id}/plans` | 需要完整合法步骤与 `expected_version`；无任意自然语言续写 |
| 确认与推进 | 操作 `preview`、`approvals`，任务 `run` | 授权按操作提交；批量确认不是原子操作 |
| 停止与撤销 | 任务 `stop`、授权及委托 `revoke` | 不撤销已提交资金动作 |
| 任务更新 | 任务详情和分页 `trace` | 首版轮询；无服务端事件推送或实时聊天流 |
| 余额与账单 | 账户和流水查询、`bills.analyze` 任务 | 账单聚合使用工具结果，不仅汇总已加载流水 |
| 待确认中心 | 任务详情中的操作、按操作查询授权 | 首版限定当前任务；全局队列和总数需补接口 |
| 证据与导出 | 任务 `evidence`、`GET /v1/export/{id}` | 不宣称当前导出包含全部长轨迹 |
| 评估与候选 | `/v1/evaluation/` 下现有入口 | 无候选全量列表；需权限及功能开关 |
| 连接配置 | `/v1/integrations/` 目录与校验 | 无持久化激活、外部探测或插件执行 |

建议首版在页面可见且任务活动时每 2 秒读取详情；等待人工确认可降为 10 秒，页面隐藏后暂停。断网按 2、4、8 秒逐步退避，最长 30 秒；恢复可见时立即重新查询。以上是待压测的交互参数，不是现有后端服务承诺。完成后读取一次详情、证据和相关账户，再停止轮询。

轨迹使用 `after` 增量读取，按 `sequence` 合并和去重。重规划、授权或执行完成后，使相关任务、预览和账户缓存失效。金融写请求关闭通用自动重试；`run_in_progress` 时等待原任务。不采用乐观更新来宣布转账成功、余额改变或授权有效。

首版无需等待所有新接口。跨会话恢复、全局待办和评估历史等扩展，先补明确的响应契约、过滤与分页接口，再开放对应导航。

## 实施顺序与验收设计

本节保留原实施顺序及进入下一阶段的条件。设计任务之后已完成首版工程；实际验收范围以[验收记录](frontend-validation.md)为准。

| 阶段 | 交付范围 | 进入下一阶段的条件 |
|---|---|---|
| F1：任务闭环 | 会话接入、任务列表、自然语言与转账表单、预览确认、状态轮询、凭证、账户查询 | 转账、重复点击、响应丢失、参数冲突和停止场景通过 |
| F2：业务扩展 | 账单报告完善、申赎、卡片、订阅、受限委托 | 到账依赖、部分完成、补偿和委托撤销可解释且与后端一致 |
| F3：开发工作台 | 轨迹、计划差异、导出、回放和候选详情 | 业务区与评估区权限隔离；发布和回退有明确审核 |
| F4：正式接入准备 | 登录会话、额外验证、连接管理、全局待办、跨会话请求恢复 | 新接口、安全边界、真实适配和部署分别验收 |

后续至少验收以下场景：

1. 示例余额 1,500 元，转账 300 元，最低保留 1,000 元。确认前无扣款；核实后显示 1,200 元执行时余额与凭证。
2. 连续点击和请求响应丢失不会创建第二笔业务；页面关闭再打开后先恢复查询。
3. 预览后修改金额，旧确认失效；版本冲突展示差异并重新确认。
4. 超过服务端额外验证门槛时，界面不能绕过拦截，也不声称身份验证已完成。
5. 银行已处理但响应丢失时，显示结果待核实；全过程不提供原操作的重新付款按钮。
6. 赎回受理后等待到账，到账证据确认后才推进依赖付款；不靠倒计时宣布到账。
7. 停止后续步骤保留已完成事实；部分完成不能显示成全部成功或全部撤销。
8. 账单跨自然月、含退款和无匹配记录时，日期、分类和净额均与工具结果一致。
9. 会话失效、无权限、断网和服务不可用有独立状态；旧数据明确标注读取时间。
10. 键盘操作、320 px 窄屏、放大文字和减少动态效果设置下，确认内容与主按钮仍可用。

本次核对了现有文档、接口实现、状态定义与设计引用。界面示意已检查 5 种状态在 4 种宽度下的布局，并检查确认、核实说明、凭证展开和验证阻断交互；同时查看了桌面、窄屏及暗色预览。以上为设计示意检查，不代表前端产品验收。

本次未运行后端回归，未执行真实业务或前端联调。聊天中的界面示意使用设计样例，切换状态不代表执行任务。
