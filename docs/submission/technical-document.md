项目版本：0.3.0（模拟业务预览版）

## 项目定位与能力边界

FinGuard 把用户目标转换为结构化计划，在服务端授权范围内推进业务，再根据权威业务记录核实结果。目标用户包括个人金融任务的原型体验者，以及需要调试金融 Agent 的开发者。

系统重点处理三个问题：计划能否完整覆盖用户条件；故障恢复是否造成重复付款；“工具调用成功”是否有充分业务证据支撑。

| 能力 | 当前实现 | 使用边界 |
|---|---|---|
| 任务工作台 | 创建、澄清、逐项确认、停止、凭证、轨迹 | 开发令牌或桌面本机会话 |
| 模拟业务 | 转账、账单、理财申赎、临时锁卡、订阅取消 | 人民币整数分与虚构资源 |
| Agent 规划 | DeepSeek 官方协议、自适应单次路径、有界循环 | 编排已验证的结构化目标 |
| 可靠执行 | 持久化意图、稳定操作编号、未知核实、重启恢复 | 下游保证由模拟银行提供 |
| 扩展准备 | 银行、模型、插件契约及本地校验 | 不激活连接，不执行用户插件 |
| 离线改进 | 隔离回放、候选评估、审核发布、回退 | 仅调整提示词，质量待持续评估 |

示例输入：“给小王转 300 元，至少保留 1,000 元。”初始模拟余额为 1,500 元。系统展示对象、金额、费用与约束，等待用户确认。确认后核实余额为 1,200 元，并关联转账记录、流水及余额证据。

实现选型：后端采用 Python、FastAPI、Pydantic、PostgreSQL、Psycopg 和 HTTPX；前端采用 React、TypeScript、Vite、TanStack Query、Zod 和无损 JSON 解析；Windows 外壳使用 pywebview 和独立冻结服务。

## 系统架构与信任边界

<!-- diagram: architecture -->

图 1：在线执行架构。模型只返回候选计划。所有业务读写均通过 FinGuard 控制边界和认证银行客户端。

| 模块 | 入口位置 | 主要职责 |
|---|---|---|
| 任务与页面 | frontend/、backend/api.py | 会话、任务、预览确认、状态及凭证 |
| 理解与规划 | understanding.py、planning.py、deepseek.py | 有限理解、候选编排、编译和循环预算 |
| 执行与授权 | service.py、security.py、authorization.py | 归属、权限、授权消费、提交及核实 |
| 银行客户端 | backend/bank.py | 认证 HTTP 调用，不访问银行数据库 |
| 独立模拟银行 | services/bank-simulator/ | 账户、账本、业务结果、结算和权威证据 |

应用事务先保存授权消费与提交意图，再调用银行的独立事务。应用不跨外部调用持有该事务。两次提交之间发生故障时，恢复进程查询原操作，核实实际结果。

项目本体与模拟银行分开源码、运行环境、配置、进程、数据库和账号。本机可共用 PostgreSQL 实例；Compose 使用独立数据库容器和卷。共享契约包只提供类型与规则，不持有业务状态。

## 领域对象与计划编译

| 对象 | 稳定关联 | 控制作用 |
|---|---|---|
| Task（任务） | 主体、客户端请求编号、目标、约束 | 请求重试去重及范围检查 |
| Plan（计划） | 任务、版本、节点和依赖 | 重规划保留已完成事实 |
| Approval（授权） | 主体、操作编号、参数摘要、期限 | 关键参数变化后重新确认 |
| Operation（操作） | 主体、任务、动作、规范参数 | 恢复与重试复用业务身份 |
| Evidence（证据） | 操作、来源、业务记录、类型 | 证明实际结果和目标达成 |

计划输入包含 step_ref、action、arguments、depends_on 和 funds_available_after。后者表达资金实际到账条件，不能由普通“申请已受理”替代。

编译流程：先检查工具注册与严格字段类型，再规范化金额、费用及最低余额；检查节点唯一、依赖完整和无环；最后核对候选与原目标的一致性。增删目标、修改收款人或金额、移除到账条件均拒绝。

金额以整数分保存，币种显式限定为 CNY。金额拒绝浮点数、布尔值和字符串；前端使用无损解析和整数计算，避免大整数在浏览器中失真。

参数摘要绑定主体、动作与规范化参数。授权不能仅绑定任务编号。变更关键参数时建立新操作并重新授权；已成功、已提交及结果未知的操作保持原身份和事实。

自然语言入口采用有限语法。所有分句须完整理解；存在未支持的条件或歧义时，整项任务进入澄清。模型目前负责结构化目标编排，不能视为任意开放文本理解服务。

## Agent 规划算法与有界循环

<!-- diagram: agent -->

图 2：规划路径。循环只开放 inspect_steps 与 submit_plan，业务工具继续由确定性内核执行。

auto 模式在目标不超过 2 个、没有资金到账条件且关闭思考模式时，采用单次紧凑候选；其余任务采用有界工具循环。loop 模式可显式强制循环。

inspect_steps 每次最多查询 8 个已校验目标，单次反馈最多 32 KiB。submit_plan 返回 completed 或 rejected，并提供明确错误码。编译通过后才进入业务控制。

默认每次规划最多 4 轮、每轮最多 8 个工具调用，并受总时限控制。系统拒绝重复调用与重复调用编号；非法工具、超时或超限均明确失败。规划失败不创建额外业务授权，也不扩大目标。

HTTPX 客户端复用连接池，并发默认上限为 4。DeepSeek 请求固定发送到官方接口，不把其密钥转发到自定义网关。不自动重发模型请求；认证、余额、限流和响应格式错误转为明确错误码。

设计参考：项目自身的 DeepSeek 设计与验收记录。DSH-OPS 的按需工具披露和紧凑反馈提供设计参照；本项目自行实现 Python 调度，未安装该插件，未开放 Shell 执行能力。

## 执行算法与故障恢复

1. 准备：解析资源，绑定主体，形成操作与参数摘要。

2. 校验：检查权限、归属、费用、余额、业务窗口和依赖。

3. 授权：匹配单次确认或受限委托，并在提交时复检。

4. 提交：在同一本地事务中消费授权并保存提交意图，再调用银行。

5. 核实：查询原操作及权威记录，处理响应丢失和未知结果。

6. 验证：核对业务记录、流水、金额、余额及任务成功条件。

| 故障或变化 | 当前处理 |
|---|---|
| 银行已生效但响应丢失 | 保持未知，按原操作查询，禁止直接重付 |
| 提交后项目进程重启 | 从持久化意图恢复，继续核实 |
| 同任务或账户并发 | 任务会话锁、账户锁和幂等记录协调 |
| 提交前停止 | 取消未提交节点，已提交节点继续核实 |
| 证据缺失或不一致 | 保持待核实，不报告业务成功 |
| 重规划或参数改变 | 保留完成与未知事实，新参数重新授权 |

模拟银行使用稳定操作编号、参数摘要和唯一流水约束。其查询栅栏可阻止不存在操作的迟到提交。这是模拟器能力，真实银行适配必须另行确认，不能把“未找到”普遍解释为“未生效”。

赎回受理与实际到账分开。后续转账只在到账证据满足条件时解锁。转账不提供自动反向付款；临时锁卡恢复属于新任务，并重新授权。

## 安全设计与可扩展接口

访问控制与业务确认分层处理。访问令牌解析主体和权限，读操作同样检查范围与归属。业务写入还需参数绑定的单次确认，或账户、对象、金额、频次与期限均受限的委托。

单次确认默认有效 300 秒，可配置范围为 1 至 3,600 秒。令牌只存摘要。执行阶段重新检查令牌、主体、授权期限和撤销状态，锁等待后仍按实际时间判断。

高金额操作采用额外验证门槛：默认总扣款超过 100,000 分时触发。当前额外验证服务不可用，因此阻止普通确认和委托执行。该门槛是开发策略，不代表银行规则。

回调默认关闭。配置后校验 HMAC-SHA256、时间窗及事件去重；回调成功声明仅作为通知，最终状态重新查询银行。请求体有大小限制，但尚无完整生产限流体系。

| 接口准备 | 已有行为 | 后续边界 |
|---|---|---|
| 银行 | 类型、能力声明、受信工厂和本地校验 | 仅注册模拟提供方 |
| 模型 | 地址、协议、消息、用量和密钥引用契约 | 通用网络客户端和密钥存储未实现 |
| 插件 | 清单、模式、配置及调用关联校验 | contract_only，不执行第三方代码 |

插件元数据启用不授予业务权限。未知提供方不回退到模拟连接。配置校验成功不表示远端可用或连接已激活。

任务文字和导出采用有限脱敏规则；隐藏推理不写入轨迹。规则不能保证识别任意秘密，导出仍需人工检查。详细风险与权限矩阵见配套安全自评报告。

## 真实模型测试与效果解释

以下为 2026 年 10 月 27 日已有验收记录，并非本次重新压测。请求及响应模型为 deepseek-flash，思考模式关闭。共 30 次真实模型请求，全部业务为虚构数据。

| 并发 | 成功 / 请求 | 成功吞吐（次/秒） | p50（毫秒） | p95（毫秒） |
|---|---|---|---|---|
| 1 | 4/4 | 1.6532 | 520.12 | 804.67 |
| 2 | 4/4 | 3.8357 | 338.88 | 721.45 |
| 4 | 8/8 | 5.4906 | 573.08 | 861.89 |

吞吐请求只要求短响应 OK，输出上限为 16 Token。16 次吞吐请求全部成功。样本量小，不代表长文本生成速度、持续容量或服务商最大并发。

| 策略 | 请求数 | 输入 Token | 输出 Token | 累计模型耗时 |
|---|---|---|---|---|
| 全量单次基线 | 3 | 3,480 | 240 | 3.00057 秒 |
| 按需工具循环 | 6 | 5,958 | 498 | 6.11967 秒 |
| 自适应简单路径 | 3 | 1,203 | 287 | 3.00890 秒 |

三个策略均覆盖有效授权、缺少授权、响应丢失三种情景。每个策略合法任务完成率为 2/2，正确处理率为 3/3。等待授权不计为业务完成。

短任务中，强制两轮循环增加开销。自适应路径相对全量基线减少约 65.4% 的输入 Token，模型累计等待时间基本相同。顺序未随机化，循环有缓存命中；结果不能作为通用性能或费用承诺。

来源：docs/deepseek-validation.md。原始本机报告的 SHA-256 见该记录；原始运行产物不打包公开。
