# DeepSeek 真实验收记录

日期：2026 年 10 月 27 日。版本：0.3.0。设计及执行协议见 [Agent 设计](deepseek-design.md)。

## 结果

已使用本机密钥调用 DeepSeek 官方 API。共执行 **30 次模型请求**，没有自动重发，未超过约定的 32 次上限。吞吐、三种规划策略和隔离 HTTP 联调均通过。全部业务使用虚构数据与独立数据库命名空间，不涉及真实银行。

请求及响应模型均为 `deepseek-flash`，思考模式关闭。吞吐请求只要求返回一个 `OK`，输出上限为 16 Token；规划输出上限为 2048 Token。API 密钥只保存在本机，不进入报告、日志或仓库。

测试分阶段执行，时间为北京时间 08:44:35 至 08:52:51，中间包含方案调整及补充验证。以下性能分别使用各阶段实测耗时，不能把整个时间跨度当作连续压测时长。

## 规划对照

三种方案使用同一组转账目标，分别覆盖有效授权、缺少授权和响应丢失。三种执行情景的规划输入相同，因此只能反映该短计划的开销，不能代表复杂任务的普遍表现。

| 方案 | 模型请求数 | 输入 Token | 输出 Token | 缓存命中输入 Token | 模型请求累计耗时（秒） | 正确处理 |
|---|---|---|---|---|---|---|
| 全量模式单次基线 | 3 | 3480 | 240 | 0 | 3.00057 | 3/3 |
| 按需工具循环 | 6 | 5958 | 498 | 2304 | 6.11967 | 3/3 |
| 自适应简单任务路径 | 3 | 1203 | 287 | 0 | 3.00890 | 3/3 |

工具循环每例经过 2 轮，在这组短任务上增加了开销。根据结果增加 `auto` 策略：最多 2 个目标、没有资金到账条件且未启用思考模式时，单次发送完整目标及相关业务模式。其余任务保留有界工具循环，也可用 `loop` 强制选择循环。

相较全量基线，自适应路径的输入 Token 减少约 **65.4%**，总输入与输出 Token 减少约 **59.9%**，累计模型等待时间基本相同。相较两轮工具循环，模型等待时间减少约 **50.8%**。这些数字仅适用于本次样本，不是费用降幅或通用性能保证。

基线先测，循环和自适应路径后测，没有随机化执行顺序。实际缓存命中已列出，模型服务负载和时间顺序也可能影响延迟。

## Agent 与业务结果

| 场景 | 三种方案的结果 | 业务核实 |
|---|---|---|
| 有效授权转账 | `COMPLETED` | 余额 120,000 分，转账只记账一次，证据齐全 |
| 缺少授权 | `WAITING_APPROVAL` | 余额保持 150,000 分，没有转账写入 |
| 银行生效后响应丢失 | 核实后 `COMPLETED` | 余额 120,000 分，沿用原操作身份，没有重复扣款 |

每种方案的合法任务完成率为 2/2，正确处理率为 3/3。等待授权不计为业务完成。授权、参数、账本、重复入账、资源归属、证据、委托预算和最低余额不变量全部通过。

另在独立 HTTP 服务与命名空间中测试了真实 DeepSeek 余额查询：经过创建任务、模型规划、执行和轨迹查询，最终为 `COMPLETED`，`verified_success: true`，生成 1 条业务证据。使用自适应单次路径，模型请求耗时 1024.03 毫秒；该服务及测试命名空间已清理。

请求数核对：连接探测 1 次、吞吐 16 次、全量基线 3 次、工具循环 6 次、自适应对照 3 次、HTTP 联调 1 次，共 30 次。
