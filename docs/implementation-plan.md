# 实施步骤

日期：2026 年 10 月 26 日。本文细化[开发路线](roadmap.md)，用于逐次开发和验收。当前已完成步骤 1 和步骤 2，下一批进入模拟银行与存储。

## 建设目标

先建立一个可恢复、可核验的模拟转账闭环，再逐步加入动态规划、交互界面和完整业务范围。

首个输入沿用[转账场景](../tests/scenarios/transfer-basic.json)：初始余额 1,500 元，转账 300 元，最低保留余额 1,000 元，费用为 0 元。首次闭环使用已确认的账户和收款人，以及固定的结构化计划。

成功需要同时满足：余额变为 1,200 元、转账仅记账一次、授权有效、业务证据完整，以及任务成功条件通过验证。

首个闭环是后续功能的验证基础，完整范围仍包括账单、理财、卡片、订阅、跨服务任务和离线策略优化。

## 工程实施方向

建议先采用模块化单体：模块通过明确契约协作，先集中部署和调试。后台核实任务可以独立运行，但共享业务对象和持久化状态。

| 项目 | 建议方向 | 引入时机与边界 |
|---|---|---|
| 后端语言 | Python | 步骤 1 确定兼容版本、依赖管理和锁定方式 |
| 服务接口 | FastAPI | 步骤 6 引入；领域规则不依赖服务框架 |
| 持久化 | PostgreSQL | 步骤 3 引入；并发验收使用实际目标数据库 |
| 自动化测试 | pytest | 步骤 1 建立入口，随模块增加用例 |
| 用户界面 | Web 任务工作台 | 步骤 7 确定前端技术，覆盖预览、授权和轨迹 |
| 模型与编排 | 可替换模型接口与显式计划控制 | 步骤 8 再确定模型服务及是否引入工作流框架 |

Python、uv、Pydantic、pytest 和 Ruff 已用于首批实现。版本及验证范围见[设计决策](decisions.md)。FastAPI、PostgreSQL、模型和界面仍按后续步骤引入。

选择 PostgreSQL 是为了在目标环境验证事务和并发控制。行锁等机制只是实现手段，正确性仍取决于事务范围和实际测试。[官方锁机制文档](https://www.postgresql.org/docs/current/explicit-locking.html)说明了相关语义。

FastAPI 的接口能力与 pytest 的测试组织方式分别参考其[官方说明](https://fastapi.tiangolo.com/)和[测试文档](https://docs.pytest.org/en/stable/)。本项目不直接采用网页上的最新版本号。

## 依次执行的步骤

| 步骤 | 对应阶段 | 主要工作 | 完成判据 |
|---|---|---|---|
| 1．建立开发基础 | P1 | 确定运行时与依赖；建立源码包、测试入口、配置示例和持续集成 | 新环境可按说明安装并运行实际存在的检查 |
| 2．实现领域与工具契约 | P1 | 五个核心对象、金额、主体归属、状态迁移和工具元数据 | 非法金额、跨主体引用、非法状态迁移及无效工具参数被拒绝 |
| 3．建立模拟银行与存储 | P1、P2 | 模拟账户、交易、账本、操作存储和查询；定义故障脚本 | 交易状态、余额和账本可以交叉核对，重启后可读取 |
| 4．实现可靠执行内核 | P2 | 稳定操作编号、幂等提交、未知结果核实和恢复；同步记录轨迹 | 重复请求、响应丢失和重启不会导致重复记账 |
| 5．接入授权与策略 | P3 | 单次授权、参数绑定、权限隔离、有效期、撤销和提交前复检 | 无有效授权时不执行；并发支出与授权消费不突破约束 |
| 6．跑通固定任务闭环 | P4 | 计划版本、依赖调度、停止、证据验证、结果报告和服务接口 | 首个转账场景及关键异常场景通过端到端验证 |
| 7．建立交互工作台 | P4、P6 | 任务输入、业务预览、授权确认、进度、停止和轨迹查看 | 用户可以看清将执行的内容，并区分成功与仍待核实 |
| 8．接入动态规划 | P5 | 意图解析、澄清、计划编译、专业角色、审查和局部重规划 | 模型输出经过控制程序；重规划保留已完成事实 |
| 9．扩展完整业务 | P5、P6 | 账单、订阅、卡片、理财和条件组合任务；逐项补齐契约和证据 | 各业务按自身语义验收，多服务部分完成可解释、可恢复 |
| 10．建设持续改进闭环 | P6、P7 | 场景回放、故障注入、指标比较、离线优化、审核与回退 | 改进有对照依据，发布可回退，系统不变量持续通过 |

步骤 4 先在隔离测试中验证执行协议。授权控制完成前，不开放可成功执行的用户写入口。控制边界从工具契约阶段就保留，缺少授权时默认拒绝。

轨迹记录、故障测试和基础回放随业务代码同步建设。步骤 10 负责将这些能力组合为完整评估和改进流程。

## 首批编码任务

以下任务已完成。当前提供可运行的领域基础和场景校验；GitHub Actions 配置已建立，远端结果单独核实。

1. 核对本机运行环境，确定版本及依赖管理方式，建立隔离开发环境。
2. 建立 `src/finguard/` 源码包、必要项目清单和可运行测试入口。
3. 实现金额与币种、稳定编号、主体与资源归属表达。
4. 定义任务、计划、授权、操作和证据的数据类型。
5. 定义合法状态迁移、终态处理和明确的领域错误。
6. 定义工具契约，区分读写、副作用、授权、幂等和查询能力。
7. 将现有转账场景整理为可加载的测试输入，并记录格式版本。
8. 运行相关检查，更新文档，提交并同步到 GitHub。

这批任务的交付是可运行的领域基础和测试，不将完整转账成功作为本批完成条件。交易存储和适配器属于下一批任务。

## 第一个闭环的验收场景

以下是步骤 3 至步骤 6 的验收目标，当前尚未实现。

| 场景 | 预期结果 |
|---|---|
| 有效授权与余额充足 | 仅产生一次转账，最终余额为 1,200 元，证据可关联到操作 |
| 缺少授权、授权过期或已撤销 | 拒绝提交，余额和账本保持原状 |
| 金额、账户、收款人、费用或约束发生变化 | 原授权重新匹配；范围不适用时等待新授权 |
| 相同操作重复提交 | 返回同一业务结果，不新增同义转账 |
| 相同操作编号对应不同参数 | 明确报告冲突，阻断第二次提交 |
| 提交前余额变化 | 重新检查保留余额条件，不满足时停止提交 |
| 两个任务竞争同一账户或授权限额 | 原子地判断可用额度，不因并发突破限制 |
| 转账已生效但响应丢失 | 进入结果未知状态，核实原交易后收敛，不直接再次付款 |
| 提交前后服务重启 | 从持久化状态恢复，已执行操作不重复记账 |
| 用户停止任务 | 未提交操作停止；已提交操作继续核实并报告结果 |
| 跨主体访问或外部文本要求越权 | 控制边界拒绝访问或指令，不改变授权状态 |
| 工具报告成功但证据不足 | 继续核实或报告未确认，不宣称任务成功 |

模拟账本可在本地事务中协调余额、账本和幂等记录。外部银行调用与本地数据库没有天然的共同事务，后续接入需单独设计提交意图、查询核实和恢复协议。

## 三个可验收里程碑

- **M1：固定转账闭环。** 步骤 1 至步骤 6 完成，关键异常场景通过，得到可复现的执行基础。
- **M2：可交互的动态任务。** 步骤 7 和步骤 8 完成，用户可输入目标、处理澄清、确认操作并查看证据。
- **M3：完整业务与持续改进。** 步骤 9 和步骤 10 完成，各业务具备明确的状态、证据和恢复语义。

每个里程碑以实际代码、场景结果和验证记录验收。模型、真实业务接口和数据条件明确后，再估算工期。
